# A股指标与卦象量化回测测试中心升级改造方案

**文档版本：** V1.0  
**编制日期：** 2026年7月21日  
**适用项目：** A股指标回测、卦象辅助策略、参数寻优与持续实验平台

---

## 一、项目改造目标

现有系统的“实验中心”主要属于固定模板的批量回测工具，能够按“指标规则 × 卦象方案 × 买卖日程模板”生成有限数量的组合并执行回测。

本次改造的总体目标，是将现有系统升级为：

> **A股指标与卦象策略研究测试中心：能够定义参数空间、持续生成实验、并行回测、自动评价、滚动验证、筛选稳健策略，并在强服务器或多服务器环境中长期持续运行。**

升级后的系统不应只回答“哪一组历史收益最高”，而应能够回答以下问题：

1. 某个指标发出信号后，优势通常能够持续几个交易日；
2. 哪种买入日期、买入时点、卖出日期和卖出时点更加稳定；
3. 叠加卦象条件后，是否真正提升收益、降低回撤或改善胜率；
4. 某组参数是否只在牛市有效，还是在熊市、震荡市中也有效；
5. 哪些结果属于偶然拟合，哪些结果具有样本外稳定性；
6. 哪些策略值得进入模拟盘、观察盘和小资金实盘验证；
7. 哪些指标参数能够形成稳定区域，而不是单一孤立的历史最优点。

---

## 二、总体改造原则

本次改造不建议推倒重建现有回测系统，而应采用“保留底层、重构实验层、强化计算层、完善评价层”的技术路线。

### 2.1 建议保留的现有能力

现有系统中以下功能可以继续保留，并在后续逐步完善：

- 通达信指标导入与指标注册；
- 日线、周线、月线和多周期共振；
- A股交易日历；
- 复权与未复权处理；
- 股票池管理；
- 组合账户与单票独立账户；
- 开盘、收盘买卖；
- 星期信号过滤；
- 止损和止盈；
- 卦象过滤；
- 涨跌停、停牌等交易约束；
- 回测结果、成交记录、权益曲线；
- Excel报告导出；
- 指标源码、股票池、行情数据和代码版本等可复现信息。

### 2.2 必须重构的部分

| 当前实现 | 改造目标 |
|---|---|
| 三个固定买卖日程模板 | 任意参数轴组合 |
| 默认上限约50组、硬上限约200组 | 支持数万至数百万候选参数 |
| Web进程内部线程执行 | 独立任务队列与多Worker执行 |
| SQLite保存实验元数据 | PostgreSQL正式实验数据库 |
| 每组重新计算指标 | 指标信号与过滤结果分层缓存 |
| 每组生成完整文件 | 普通实验只存摘要，优胜组生成详情 |
| 参数哈希只看请求参数 | 完整研究指纹 |
| 只比较收益、回撤、胜率 | 多目标、样本外和稳定性评价 |
| 手动刷新查看进度 | 实时进度与Worker监控 |
| 服务重启可能丢失任务 | 支持暂停、恢复、重试和断点续跑 |
| 一次性实验 | 日常、夜间、周末和月度持续研究计划 |

---

## 三、目标系统总体架构

建议将系统升级为以下七层架构：

```text
研究配置页面
      ↓
参数空间生成器
      ↓
实验规划与合法性检查
      ↓
任务队列
      ↓
多进程 / 多服务器回测 Worker
      ↓
PostgreSQL 实验数据库 + 信号缓存 + 结果存储
      ↓
排名、热力图、样本外验证、稳健性分析
```

建议新增研究模块：

```text
wtpy/apps/astock/research/
├── models.py             参数、实验和任务模型
├── parameter_space.py    参数空间定义与展开
├── constraints.py        非法组合过滤
├── planner.py            实验规划与任务生成
├── fingerprint.py        研究指纹
├── signal_cache.py       指标信号缓存
├── filter_cache.py       卦象及其他过滤结果缓存
├── executor.py           单组实验执行
├── optimizer.py          网格、随机、智能寻优
├── validation.py         样本外与滚动验证
├── scoring.py            综合评分与Pareto排名
├── regimes.py            牛市、熊市、震荡市划分
├── tasks.py              Celery任务
└── reports.py            实验报告生成
```

现有模块建议按以下方向调整：

- `service/experiments.py`：由固定组合批跑器改为实验编排接口；
- `service/backtest.py`：拆分指标信号计算、交易执行和报告生成；
- `strategy.py`：升级交易日程、退出优先级和批量执行逻辑；
- `data/calendar.py`：增加节假日顺延策略；
- `service/db.py`：抽象数据库访问并迁移PostgreSQL；
- 前端实验中心：由单一固定页面升级为模块化参数配置页面。

# 四、核心改造一：建设参数空间中心

## 4.1 取消固定买卖日程模板限制

现有“研究常用日程”“经典T+1/T+2”“周五买、下周一平”等整体模板，可以继续作为快捷预设保留，但不能再作为系统唯一的参数入口。

系统应允许用户分别设置每一个独立参数轴。

---

## 4.2 指标参数轴

应支持：

- 单个指标；
- 多个指标组合；
- AND关系；
- OR关系；
- 指标按顺序确认；
- 日线；
- 周线；
- 月线；
- 日周月共振；
- 指标内部参数。

以735指标为例，可以将固定公式参数化：

```text
短均线周期：[5, 7, 10]
长均线周期：[20, 30, 35, 60]
偏离阈值：[1%, 2%, 3%, 5%]
是否要求短均线上升：[是, 否]
是否要求长均线上升：[是, 否]
```

建议指标定义支持如下参数结构：

```json
{
  "rule_id": "735",
  "parameters": {
    "short_ma": {
      "type": "int",
      "default": 7
    },
    "long_ma": {
      "type": "int",
      "default": 35
    },
    "dev_threshold": {
      "type": "float",
      "default": 2.0
    }
  }
}
```

这是系统实现“持续测试每个指标不同情况”的关键基础。

---

## 4.3 信号参数轴

应支持：

- 信号星期：周一至周五、不限制；
- 信号确认时点：盘中、收盘；
- 信号有效期：当日、1个交易日、2个交易日等；
- 连续信号处理：首次、每次、合并；
- 信号冷却期；
- 周线、月线信号确认日期；
- 同一指标重复触发的处理方式。

---

## 4.4 买入参数轴

应同时支持两种模式。

### 模式一：交易日偏移模式

例如：

```text
信号后第1个交易日开盘买
信号后第1个交易日收盘买
信号后第2个交易日开盘买
信号后第2个交易日收盘买
```

### 模式二：星期锚定模式

例如：

```text
周五收盘确认信号
下周一开盘买
下周一收盘买
```

还应支持：

- 信号当天买入；
- 次日买入；
- 延迟N个交易日买入；
- 指定星期买入；
- 开盘买入；
- 收盘买入；
- 均价买入；
- 涨停无法买入处理；
- 停牌处理；
- 买入日休市处理。

---

## 4.5 卖出参数轴

至少支持：

- 买入后第N个交易日退出；
- 指定星期退出；
- 开盘退出；
- 收盘退出；
- 止损退出；
- 止盈退出；
- 移动止损；
- 指标反向信号退出；
- 卦象转弱退出；
- 最大持有期；
- 多个退出条件取最先触发；
- 多个退出条件按优先级执行。

建议每笔交易保存具体退出原因：

```text
stop_loss
take_profit
time_exit
weekday_exit
reverse_signal
gua_weakening
forced_exit
delisting_exit
```

---

## 4.6 卦象参数轴

应支持：

- 不加卦象；
- 最佳三爻；
- 偏多操作信号；
- 单个爻分别测试；
- 多个爻组合；
- 主卦分别测试；
- 变卦分别测试；
- 主卦与变卦组合；
- 自定义爻集合；
- 自定义主卦集合；
- 技术信号与卦象的AND关系；
- 技术信号与卦象的OR关系；
- 卦象作为过滤条件；
- 卦象作为评分权重；
- 卦象作为退出条件。

所有卦象规则必须版本化，确保历史实验可复现。

---

## 4.7 风险和交易参数轴

应支持：

- 止损：[无、2%、3%、4%、5%等]；
- 止盈：[无、5%、8%、10%、15%等]；
- 移动止损；
- 仓位比例；
- 最大持仓数量；
- 单票最大仓位；
- 等权分配；
- 信号评分加权；
- 手续费；
- 印花税；
- 滑点；
- 涨跌停无法成交处理；
- 停牌处理；
- 退市处理；
- 资金不足处理；
- 同日多个信号资金竞争处理。

# 五、参数组合与合法性约束

参数不能简单无条件相乘，必须增加合法性检查。

例如：

- 周五收盘确认信号，不能以周五开盘价买入；
- 收盘后才能确认的信号，不能假设以同一收盘价无滑点成交；
- A股普通股票买入后不能当天卖出；
- 卖出时间不能早于买入时间；
- 周线指标不能使用尚未完成的本周最终数据；
- 月线指标不能使用尚未完成的当月最终数据；
- 指定卖出星期与最大持有期冲突时，必须明确优先级；
- 同时设置固定卖出日和持有N日时，必须明确退出规则；
- 买入或卖出日期遇到节假日时，必须按照配置处理。

参数组数应计算为：

```text
理论组合数
− 时间逻辑非法组合
− A股交易制度非法组合
− 数据不足组合
− 用户排除组合
＝ 实际运行任务数
```

实验开始前，页面必须展示：

- 理论组合数；
- 被过滤组合数；
- 实际运行组数；
- 每类过滤原因；
- 前50组参数预览；
- 股票数量；
- 数据区间；
- 搜索方式；
- 任务优先级；
- 预计数据读取规模。

# 六、735指标标准验收案例

建议将735指标作为新实验中心第一版的标准验收案例。

## 6.1 固定条件

- 周五收盘确认735信号；
- 下周一开盘买入；
- 不设止损；

```text
= 16组
```

| 周三开盘 | 回测结果 | 回测结果 | 差异 |
| 周三收盘 | 回测结果 | 回测结果 | 差异 |
| 周四开盘 | 回测结果 | 回测结果 | 差异 |
| 周四收盘 | 回测结果 | 回测结果 | 差异 |
| 周五开盘 | 回测结果 | 回测结果 | 差异 |
| 周五收盘 | 回测结果 | 回测结果 | 差异 |

## 6.4 每组必须比较的指标

- 最大回撤；

- Sortino比率；

- 盈亏比；
- Profit Factor；
- 成交回合；
- 交易次数；
- 信号数量；
- 卦象过滤后的信号保留率；
- 交易成本；
- 不同年度表现；

- 样本外表现；
- 参数邻域稳定性。

# 七、核心改造二：将完整回测拆成三层

现有系统如果每一种组合都重新读取行情、计算指标、叠加卦象和生成报告，将造成大量重复计算。

应将回测拆为三层缓存。

---

## 7.1 第一层：指标信号层

唯一键建议包括：

```text
行情数据版本
+ 股票池版本
+ 指标公式版本
+ 指标参数
+ 周期
+ 起止日期
+ 复权模式
```

输出内容包括：

- 股票代码；
- 信号日期；
- 信号类型；
- 指标参数；
- 指标值快照；
- 周期；
- 公式版本。

同一指标、同一参数、同一股票池、同一区间只计算一次。

---

## 7.2 第二层：信号过滤层

唯一键建议包括：

```text
原始信号缓存ID
+ 信号星期
+ 卦象规则版本
+ 卦象筛选条件
+ 其他过滤条件
```

输出示例：

- 周五735信号集合；
- 周五735加最佳三爻信号集合；
- 周五735加偏多卦象信号集合。

---

## 7.3 第三层：交易执行层

针对同一批信号，快速测试：

- 不同买入日；
- 不同卖出日；
- 开盘或收盘；
- 不同持有期；
- 不同止损；
- 不同止盈；
- 不同仓位；
- 不同账户模式。

通过分层缓存，735的16组实验无需重复计算16遍指标。

# 八、建设两种回测引擎

## 8.1 快速研究引擎

用于大规模参数初筛。

主要计算：

- 每个信号对应的买入价格；
- 每种退出日期的价格；
- 每笔交易收益；
- 胜率；
- 盈亏比；
- 收益分布；
- 持有周期；
- 不同股票和时间段的表现。

快速研究引擎暂时不进行复杂资金竞争和组合账户模拟，以提高运行速度。

## 8.2 完整精确回测引擎

用于最终候选策略。

应完整处理：

- 资金账户；
- 最大持仓数量；
- 同日多个信号；
- 资金不足；
- 仓位控制；
- 涨跌停；
- 停牌；
- 退市；
- 手续费；
- 印花税；
- 滑点；
- 实际成交；
- 组合权益曲线；
- 完整成交记录。

建议采用：

```text
快速研究引擎筛选数万组
        ↓
选出前1%～5%
        ↓
完整组合引擎精确复测
        ↓
样本外验证
        ↓
模拟盘验证
```

# 九、核心改造三：任务队列与持续运行平台

当前Web进程内部使用线程执行实验，不适合长期大规模运行。

建议采用：

```text
FastAPI：接收请求和展示结果
Redis或RabbitMQ：任务队列
Celery Worker：执行任务
PostgreSQL：保存实验和任务
Celery Beat：定时生成研究任务
```

## 9.1 建议任务队列

```text
signal_queue       指标信号计算
fast_backtest      快速参数初筛
full_backtest      完整精确回测
validation_queue   样本外与滚动验证
report_queue       Excel和报告生成
maintenance_queue  数据检查和缓存维护
```

## 9.2 每个任务必须支持

- 排队；
- 运行；
- 暂停；
- 恢复；
- 取消；
- 超时；
- 自动重试；
- Worker失联后重新领取；
- 服务重启后继续；
- 心跳检测；
- 失败原因记录；
- 单组重新运行；
- 整个实验重新运行；
- 任务优先级；
- CPU和内存限制；
- 最大重试次数；
- 幂等执行。

# 十、长期持续运行机制

“服务器一直跑”不应理解为无限制随机生成参数，而应建立正式的研究计划。

## 10.1 日常计划

每次行情数据更新后：

- 更新行情版本；
- 更新复权因子；
- 检测重点指标最新信号；
- 重跑重点候选策略；
- 检查最近表现漂移；
- 更新模拟盘候选。

## 10.2 夜间计划

- 运行小规模参数搜索；
- 更新年度表现；
- 更新行业表现；
- 更新市场阶段表现；
- 重试失败任务；
- 生成次日研究摘要。

## 10.3 周末计划

- 全股票池测试；
- 更大参数空间搜索；
- Walk-Forward滚动验证；
- 交易成本压力测试；
- 滑点压力测试；
- 候选策略精确复测；
- 卦象增量对照；
- 参数稳定性分析。

## 10.4 月度计划

- 重新划分市场状态；
- 重新评价候选策略；
- 检查指标是否失效；
- 检查参数漂移；
- 形成月度研究报告；
- 调整研究优先级。

## 10.5 实验预算

每个研究计划必须设置：

- 最大组合数；
- 最大运行时间；
- 最大CPU时间；
- 最大内存；
- 最大磁盘占用；
- 最大失败次数；
- 最低改善阈值；
- 提前停止条件；
- 最终精确复测数量。

# 十一、核心改造四：迁移PostgreSQL实验数据库

SQLite可继续用于本地开发，但正式服务器建议迁移PostgreSQL。

建议数据表包括：

# 十三、修复星期与节假日逻辑

当前“寻找下一个指定星期交易日”的方式可能导致目标星期休市后，直接等待到下一周同一星期。

应新增节假日处理策略：

```text
next_trading_day      顺延至下一个交易日
previous_trading_day  提前至前一个交易日
skip_trade            取消本次交易
exact_weekday_only    必须为指定星期，否则取消
```

建议默认：

- 买入日休市：顺延至下一个交易日；
- 卖出日休市：顺延至下一个交易日；
- 顺延后若超过最大持有期：按配置执行；
- 保存计划成交日期和实际成交日期。

每笔交易应保存：

```text
planned_entry_date
actual_entry_date
entry_shift_days
planned_exit_date
actual_exit_date
exit_shift_days
holiday_policy
```

# 十六、搜索算法分级建设

## 16.1 第一级：网格穷举

适合：

- 星期；
- 开盘或收盘；
- 是否叠加卦象；
- 少量止损止盈；
- 735这类离散参数。

这是第一阶段必须完成的能力。

## 16.2 第二级：随机与分阶段搜索

适合：

- 指标内部参数较多；
- 理论组合数达到几十万以上；
- 先进行粗搜索；
- 再对较优区域进行精细搜索。

## 16.3 第三级：Optuna智能寻优

建议支持：

- GridSampler：离散网格；
- RandomSampler：随机初筛；
- TPESampler：大参数空间；
- NSGA-II：收益、回撤和稳定性多目标优化；
- Pruner：明显较差的单目标实验提前停止；
- 固定随机种子：保证研究可复现。

被提前停止或智能筛选出的候选策略，最终必须使用完整精确回测重新跑完。

# 十七、综合评分与筛选规则

系统不应只使用一个收益率作为评价标准。

## 17.1 硬门槛

建议先设置：

```text
交易次数 ≥ 最低样本量
最大回撤 ≤ 用户上限
样本外盈利窗口占比 ≥ 最低要求
最近区间不能严重失效
不能由极少数股票贡献全部收益
交易成本后仍为正收益
```

## 17.2 综合评分

通过硬门槛后，再计算综合评分：

```text
综合分 =
样本外风险收益分
+ 时间稳定性分
+ 横截面稳定性分
+ 参数邻域稳定性分
− 回撤惩罚
− 交易成本惩罚
− 过拟合惩罚
```

## 17.3 Pareto前沿

系统应同时保留多种候选：

- 收益高但回撤较大；
- 收益略低但更稳定；
- 交易次数少但信号质量高；
- 叠加卦象后回撤明显下降；
- 最近年份表现更好；
- 样本外表现更加稳定。

不能强行只输出一个唯一第一名。

# 二十、服务器部署建议

该系统主要属于CPU、内存和磁盘I/O密集型任务，不应优先购买GPU服务器。

## 20.1 第一阶段单服务器建议

- CPU：32至64个高性能核心；
- 内存：128GB起步，建议256GB；
- 磁盘：2TB以上企业级NVMe；
- 数据盘与数据库盘尽量分开；
- Linux系统；
- Docker Compose；
- PostgreSQL；
- Redis；
- 多个Celery Worker；
- Nginx；
- Prometheus；
- Grafana。

Worker并发数不能直接等于CPU线程数，必须通过基准测试确定。

## 20.2 多服务器阶段

建议架构：

```text
1台控制节点
+ 1台PostgreSQL数据库节点
+ 多台回测Worker节点
+ 共享对象存储
```

当未来需要超大规模多节点资源调度时，再评估Ray Tune，不建议第一阶段就全面迁移到Ray。

# 二十四、最终建设目标

完成全部改造后，系统应形成以下闭环：

```text
指标定义与参数化
        ↓
创建研究假设
        ↓
定义参数空间
        ↓
自动生成合法组合
        ↓
快速大规模初筛
        ↓
完整精确回测
        ↓
样本外和滚动验证
        ↓
市场阶段与参数稳定性分析
        ↓

        ↓

        ↓

        ↓

```

最终系统不再只是一个回测页面，而是一个能够长期运行、持续积累研究结果、比较指标和卦象增量价值、筛选稳健策略的专业量化研究测试中心。
