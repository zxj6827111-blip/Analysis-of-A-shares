## 3. 上线前必须处理

### R3-01 / P2：筛选范围改变后，旧结果仍被当作当前结果，甚至可继续导出

位置：`wtpy/apps/astock/web/static/index_v3.html:14427` 的 `wbImportPickedFromQuery`、`:14419` 的 `wbScreenChanged`、`:14634` 的 `wbPollScreenJob`、`:14773` 的 `wbRenderScreenJob`。

**反例 A：已完成结果的范围被替换。全部使用真实本地数据。**

1. 指定 600033、600000，2026-09-11，使用 735 规则筛选，命中 600033。
2. 在查询页只查询 600000，然后返回筛选页点击「从查询结果导入范围」。
3. 已选列表变成只有浦发银行，摘要显示「指定 1 只（查询结果）」。
4. 结果区却继续显示旧的「范围 2、命中福建高速」，「导出本次筛选结果（1 只）」仍可用。
5. 点击后实际带入导出的仍为 `SSE.STK.600033`，与用户刚导入的股票范围不一致。

截图见 `output/review-r3/stale-screen-scope.png`。根因是导入函数只重绘范围和摘要，没有清除旧 snapshot，也没有标记结果已过期。

**反例 B：在途结果会把已失效的结果重新显示出来。**

1. 仅对 600000 提交真实筛选，在浏览器暂缓 `/result` 的真实响应。
2. 等待期间手动增加 600033，列表和摘要变成 2 只，旧结果已隐藏。
3. 放行之前的真实响应，结果区又显示「范围 1、命中 0 只」。
4. 表单已是 2 只，结果却来自旧的 1 只；代码没有用请求时的条件版本保护异步结果。

这里只延迟真实响应，没有伪造筛选计算结果。因此仅在导入函数补一次 `wbScreenChanged()` 还不够。

**最小整改：**

- 所有范围、规则、日期、组合方式变更，统一走筛选条件失效逻辑；包括「从查询结果导入范围」。
- 提交前固定筛选条件快照及版本，轮询、结果渲染和导出入口验证该快照是否仍对应当前条件。
- 旧任务可继续执行或保留记录；如果结果与当前表单不符，必须明确标注旧条件并要求显式使用旧结果，或保持当前结果区失效、提示重新筛选。不可静默恢复成“本次结果”。
- 添加两条行为测试：已完成后替换范围、计算期间修改范围。断言结果和导出代码集合，不只断言源文件含某函数名。

### R3-02 / P2：提交锁依赖按钮 DOM，切换页签后能够重复提交相同导出

位置：`wtpy/apps/astock/web/static/index_v3.html:14965` 的 `wbRunExport`、`:15125` 的 `wbRenderSummaries`，尤其末尾导出按钮 disabled 赋值（`:15178`）。筛选提交入口 `:14580` 也存在收到 POST 响应后才设置 busy 的相同时间窗，需要一并核对。

**本地浏览器反例：**

1. 配好福建高速、2026-09-11、Tushare 前复权、735 附加规则。
2. 拦截并暂缓导出 POST；第一次点击后按钮确实被禁用。
3. 切到「查卦象」再返回「批量导出」，第一笔请求仍未返回，提交按钮却重新启用。
4. 再次点击，捕获到 **2 次完全相同的 POST**。

本次两笔重复请求都由浏览器拦截后返回测试用 503，**没有送到后端创建重复任务**。问题不是推测“可能点两次”，而是已经观察到前端实际发出两次请求。独立的正常导出任务已在第 1 节完成验证。

根因：提交时仅设置 `btn.disabled`，但 `wbRenderSummaries()` 根据表单是否有效重新赋值；没有独立 submitting 状态，入口也没有重入保护。真实慢响应下会增加重复计算和导出记录，全市场任务的代价更高。

**最小整改：**

- 为导出和筛选分别加入 submitting 状态，在第一次 await 前设置；函数入口遇到 submitting 直接返回，finally 统一解除。
- 摘要重绘、切页签和条件变更都必须尊重提交状态；筛选应区分 submitting 与已有 job 的 running。
- 成功收到任务 ID 后允许用户按产品规则主动新建任务，不必把整个后台生成阶段全部锁死。
- 补浏览器或 DOM 行为测试：延迟 POST → 切页签 → 返回 → 尝试再次提交，断言 POST 数量始终为 1；失败后按钮可恢复。

## 4. 非阻断体验修正

### R3-03 / P3：筛选候选列表绕过“只接收股票”的检查

位置：`wtpy/apps/astock/web/static/index_v3.html:14538` 至 `:14554`。

实际输入 `000001`，候选中同时出现平安银行和上证指数；点击上证指数，成功加入筛选 chip，摘要把它计入「指定 N 只」。单候选处理有 `wbSymType(it.type) !== 'STK'` 检查，多候选点击处理没有。

后端已有非股票排除/拒绝保护，因此本项不作为独立上线阻断。建议在筛选候选显示及点击两个阶段统一类型校验，指数/ETF 不可选或明确说明不参与筛选；导出页继续允许其原有范围。当前测试仅断言函数中存在类型判断字符串，没有覆盖多候选实际点击。

其他可后续优化的文案：股票专用样本实际工作表是 `meta`、`stock-all`、`735`，没有空的 `etf-all`；页面可以把说明改为“按所选标的生成股票/ETF工作表”，避免让人误以为所有文件都固定包含空 ETF 表。不需要为文案强行改变既有导出格式。
