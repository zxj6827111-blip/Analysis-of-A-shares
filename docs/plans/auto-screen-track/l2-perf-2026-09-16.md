# L2 周明细首屏性能整改（2026-09-16）

> 本轮范围：首屏阻塞解除 + 卦象分批补齐 + 版本化缓存 + 规则身份（指纹）修复 +
> 周/月状态分开。**窗口化优化（把"全部卦象补齐总时长"从 35s 量级压到 10s 量级）
> 不在本轮**，单独立项，见 §6。

## 1. 问题与实测证据

改造前后都用同一批真实数据测过（本机 `MARKET_DATA_ROOT=E:\AStockData\datasets\market_data`）：

| 分段（信号周 2026-07-31，739 行 / 482 只票） | 改造前 | 说明 |
| --- | --- | --- |
| 快照读取 | 1.6~3.0 ms | 非瓶颈 |
| 跟踪产物读取（1.5MB JSON） | 12~27 ms | 非瓶颈 |
| 行/待结算构建 | ~2 ms | 非瓶颈 |
| **周卦+月卦补充** | **26 720 ms（占 99.7%）** | 逐票串行、挡在返回之前 |
| 接口总耗时 | 26.9 s（首次）/ 14.9 s（session 热） | 整张列表都在等卦象 |

逐票成本构成（单票热态约 32 ms，cProfile 采样）：

- `materialize_symbol`（全历史物化 5 500+ 根日线，构造 MarketBar/DayBar 对象）≈ 18 ms；
  原先 `_enrich_rows_with_bagua` 不传 session，多周期共享物化快路径直接失效 →
  WEEK/MONTH **各物化一次**，白翻一倍；
- `build_period_bars` 把 5 500 根日线整段聚合成周/月线后只取 1 根 ≈ 26 ms（每股两周各一次）。

**线程池对本负载无加速**（串行 31.7 ms/股 vs 4 线程 34.3 / 8 线程 35.2）：耗时集中在
GIL 保护的 Python 循环（对象构造与聚合），不是等待 IO。故本轮未引入并发。

## 2. 改造内容

### 2.1 列表与卦象分开加载（默认行为变更）

`GET /api/v1/bagua/track/weeks/{asof}` 新增 `bagua` 参数：

- `defer`（**默认**）：只回名单/价格/收益/统计卡片；行上 `week_gua=""`、`bagua=null`、
  `bagua_state="pending"`、`bagua_month_state="pending"`；
- `inline`：旧行为（同步算完再返回），保留给需要单请求拿全量的调用方与回归比对。

响应另带 `bagua_mode`、`bagua_total`、`bagua_cache`（inline 时的缓存命中数）、
`rule_id`/`fingerprint`/`rule_ids`（规则身份回带）与 `timings_ms`
（`snapshot_ms`/`track_ms`/`rule_filter_ms`/`rows_ms`/`pending_ms`/`bagua_ms`/`total_ms`）。

### 2.2 卦象批量补齐接口

`GET /api/v1/bagua/track/weeks/{asof}/bagua?codes=A,B,C[&rule_id=...][&fingerprint=...]`

- 名单与明细接口**同一实现**（`_load_week_rows`）→ 前端拿到的卦象键必然与表格行对得上；
- 只接受本周名单内的代码，其余进 `skipped_codes` 原样回报（不静默丢弃）；
- 单批封顶 200（`BAGUA_BATCH_MAX_CODES`），前端按展示顺序 60 只一批（`WBT_BAGUA_CHUNK`）；
- 每项带 `state`（ok/empty/error）与 **`month_state`**（周/月分开记账）；
- 响应带 `snapshot_id` + `tracking_revision_id` + `fingerprint`，前端校验一致才合并。

### 2.3 规则身份：canonical id 落到该周实际记录的兄弟 id

**问题**（用户 2026-09-16 复核，属既有缺陷但位于点击主路径）：L0 把同公式的多个 id
归并成一行并给出 canonical（如 `tn6_735金叉及趋势`），但某周快照可能只记录了兄弟 id
（`txt_735金叉及趋势`）。旧实现只按传入 id 过滤 → 该周 L1 显示 83 只、L2 却显示
「该周暂无已结算明细」。复现：`?rule_id=tn6_…` → 0 行；`?rule_id=txt_…` → 83 行。

**修法**（`_resolve_week_identity`，明细与补齐两个接口共用）：

1. 请求参数 `fingerprint`，**显式指纹是硬约束**：只取本周快照里指纹相符的 rule_id，
   入口 id 与指纹冲突时**不再无条件保留入口 id**；指纹在本周快照里没有记录 →
   `source="param_unmatched"`，返回空名单并在页面明说「该版本本周没有名单」
   （不复用入口 id 的名单，也不拿另一个版本冒充）；
2. 未给指纹时用本周快照自己的 `rule_fingerprints[rule_id]`（`source="snapshot"`）；
3. 本周没有该 rule_id 时回看历史快照反查最近指纹，且该指纹**必须在本周快照里存在**
   才采用（`source="history"`，限 26 周，命中即停）；反查不到则退化为只按入口 id
   （`source="entry_only"`，与旧行为一致）。

绝不做 `tn6_`/`txt_` 前缀替换，也不用当前规则目录覆盖历史版本。前端侧：L0 行带
`data-wbt-week-fp`，L1 周行优先用 `recorded_rule_id`（该周实际记录的 rule_id）并带
`rule_fingerprint`；明细与补齐请求用同一身份，响应回带 `fingerprint` 供补齐复用。

**每组选代表规则，不做并集**（用户复核的反例：同指纹 R 命中 A、S 命中 A、B → L0 选 R
得 1 只，旧实现并集去重得 2 只，两者口径不等价且并集是"默默"发生的）：现在
`_select_representative_rules` 与 L0 的 `_merge_by_fingerprint` 完全对齐——组内优先
`pick_canonical_rule_id`（规则中心可见/可执行者优先），canonical 本周没有产物行时用
兄弟补位；组内多个 id 都有数据且数量不一致时，响应给
`rule_identity.sibling_divergence`，页面在表头挂「ⓘ 同公式产物不一致」角标（悬停见
各 id 的行数/命中数），**不静默取并集**。展示与统计（入选数、胜率、覆盖率）都来自
代表规则那一份名单。

### 2.3.1 L1 的版本冲突

`/rules/{rule_id}/weeks` 同样按版本取数：给了 `fingerprint` 就只认该指纹的规则；
入口 id 存在但指纹不同（该周是另一个版本）时不再拿它的数据，而是给出
`version_conflict: true` 的周行（统计列显示「—」、状态列标「版本不符」、周明细按钮
禁用），让"这周怎么没数据"变成一句可读的解释。

### 2.4 周/月状态分开（月卦失败不得当成功缓存）

`bagua_week_month_info` 返回 `week_state` / `month_state`（ok/empty/error）：

- 周卦成功、月卦查询失败 → `state="ok"`（周卦是真的）、`month_state="error"`、
  `bagua.month=None`，前端只把月卦面板标「计算中/未取到，可重试」；
- **不缓存**这种"半成功"（否则月卦永远不会被重算，重试只是回放残缺结论）；
- 反向（周卦失败但月卦成功）也如实保留月卦结果，整体按周卦状态标。

### 2.5 版本化结果缓存（service/bagua_query）

缓存键 = `(std_code, week_asof, month_asof, 两个价格面各自的 materialize_key, 知识库文件指纹)`：

- overlay_v1 下 `materialize_key` 含 dataset_id（内嵌 delta watermark 与提交序号）+
  manifest_sha256 + blob_sha256 → **行情一更新就换代，旧卦象自动失效**；
- 知识库按「路径+大小+mtime」入键 → 语料替换同样失效；
- 两面都解析不出符号时不读不写缓存（版本不明宁可多算）；LRU 上限 4096；
- **error 结果不入缓存**（周卦或月卦任一 error 都不入）。

### 2.6 前端（index_v3.html）

- `wbtOpenWeek` 渲染完列表后另起 `wbtLoadWeekBagua()`，不阻塞首屏；
- 分批请求、逐批回填重绘，状态条显示「周卦补齐中 n / total …」；
- **中断语义**：`AbortController.abort()` 让客户端停止继续发批、丢弃在途响应；
  **服务端已开始的那一批会算完**（服务端循环没有取消检查）——不能声称"服务端也停了"；
- **保留与续传**：离开 L2 只中断、不清空已补结果；`wbtOpenWeek` 重进时传
  `wbtBaguaRetryCodes()`（缺的那批）而不是"补全周"，所以同周重进只补缺的票；
  `wbtLoadWeekBagua` 只有在**不传 codes**（= 重新补齐整周）时才 `wbtResetBagua()`，
  传空数组表示"没有缺的"，直接返回不清结果；换周/换规则才清空；
  跟踪版本（`tracking_revision_id`）变了才作废重取；
- 每批校验 `week_id + snapshot_id + tracking_revision_id`，不一致即停并提示；
- 三态渲染：周卦列「计算中…/无数据/计算失败」，详情面板周、月两张卡各自判状态，
  未算完不显示成 `—` 或「一般」这类结论；
- **排序与显示同源**：`wbtL2SortValue` 走 `wbtRowBaguaPart`（原实现读行内原始字段，
  首屏为空 → "显示乾为天、排序值为空"）；
- **覆盖率标注两种范围**：副标题的 `coverage` 来自整周产物（该周全部规则一起算），
  标为「覆盖率（整周全部规则）」；KPI/警示横幅里的数字来自当前规则名单
  （`ui_summary.*_coverage_exec`），横幅标「（当前规则名单）」。两者不是同一范围，
  不标会混读（用户复核指出：2026-08-28 本组是 391/391 = 100%，99.95% 是整周字段）；
- 失败/半成功时状态条给「重试」按钮，重试集合包含 `state=error` 与 `month_state=error`。

## 3. 验收方法与结果

工具：`python tools/bench_track_l2_timing.py --week 20260731 [--rule ...] [--fingerprint ...]`
（纯 HTTP，可直接在服务器上打 8080；`--inline-only` 取冷态基线）。

**与改造前等价**：`--legacy-check N` 在仓库内运行改造前的逐票实现
（`_legacy_week_month_info`，逐行取自 commit 802f8a0）并逐票比对周卦/月卦文本。
本机实测：2026-08-14 全周 **0/83 差异**、2026-07-31 的 735 组 **0/112 差异**（含去重后的同一组）。
注意工具里的 `[5] 内部一致性`（批量补齐 vs inline）两者调用**同一个新实现**且共享缓存，
只能证明接口之间一致，**不能**当作与改造前等价的证据。

本机实测（冷态）：

| 场景 | 结果 |
| --- | --- |
| defer 首屏（739 行） | **0.062 s**（响应 307KB~1MB） |
| 二次首屏 | 0.014~0.063 s |
| 周卦分批补齐 482 只 | 35.7 s / 8 批，首批 7.7 s（用户看到前排周卦的时间） |
| 重复补齐（全缓存） | 0.020~0.061 s |
| inline 冷态基线（83 行小周） | 5.78 s（其中卦象 5.73 s） |
| 与改造前实现比对 | 0/83、0/112 差异 |

浏览器实测（真实点击路径）：

- 明细请求 43 ms 落地渲染，周卦列「计算中…」，KPI/横幅/表头就绪 → 分批回填 → 状态条消失；
- 规则身份：L0「735金叉及趋势」→ L1 → 2026-08-14 周明细，按钮带
  `data-wbt-week-rule=txt_…` + `data-wbt-week-fp=d3f513487e4c89df`，页面渲染 **83 行**
  （修复前为 0 行/「该周暂无已结算明细」）；2026-07-31 该组 L1 与 L2 都是 112 行、
  胜率同为 36.61%，副标题显示「覆盖率（整周全部规则）：信号收盘 99.86%…」；
- 硬约束实测（2026-07-31）：`rule_id=tn6_735金叉及趋势&fingerprint=d3f5…` → 112 行；
  换成另一公式的指纹 `e5687f…`（量比增强）→ **21 行、只含量比增强那一条**；
  指纹取不存在值 → **0 行 + `source=param_unmatched`**（不回落入口 id）；
  不带指纹 → 112 行（历史反查，`source=snapshot/history`）；
  明细与批量补齐在三种身份下名单完全一致（`skipped=0`），版本无匹配时两边都为空；
- 周卦排序：点表头后升/降序均按**显示值**排列（83/83 非空且序列有序）；
- 中断与续传：2026-08-28 补到 180/391 时返回 L1 → 同周重进后为 **240/391**
  （已补的 180 条保留并继续，未从 0 重来）；
- 失败与重试：补齐中途停服务 → 状态条「周卦补齐中断：…」+ 重试按钮，已补的行保留，
  列表与统计不受影响；重启服务后点「重试」续传至全部补齐。

测试：`test_track_routes.py`（41 例，含显式指纹硬约束、不存在指纹、L1 版本冲突、
代表规则不取并集、canonical 无产物时兄弟补位）、`test_track_bagua_cache.py`（12 例，
含周/月状态）、`test_track_ui.py`（39 例，含排序同源/续传/口径标注/冲突角标）、
`test_track_bagua_callchain.py`（**执行调用链**：在 node 里抽出前端函数真实跑
`wbtOpenWeek → wbtLoadWeekBagua`，断言首次请求 [A,B]、离开保留 A、重进只请求 [B]、
全部补齐后再重进不发请求；把这次修的调用链改回旧写法时该测试会失败——已验证）。
全量 `pytest tests/` 见提交说明；已知既有失败
`test_tdx_compat_integration.py::test_backtest_namelike_filters_st_and_cache_key_tracks_name`

## 4. 已知遗留与下一步

1. **窗口化优化（下一轮单独立项）**：单票仍是「全历史物化 ≈18 ms + 全序列周/月聚合 ≈26 ms
   只为取 1 根周期线」。建议先做窗口化聚合、再评估窗口化物化，每步单独与旧实现对照；
   保留旧路径用于回退，按真实行情逐项比较卦象、信号、日期与数据状态。裁剪会影响前一
   周期、短周、停牌、月末锚点与复权语义，必须独立验证；10 秒只作为目标，不预先承诺。
2. **服务端无取消检查**：客户端中断后，服务端当前批次仍会算完（单批 ≤200 只，约 4~7 s）。
   如果将来要真正省下这部分算力，需要在批次循环里加协作式取消（例如按请求断开事件
   检查），属独立改动。
3. **未过滤视图（不带 rule_id，仅 API 可达）**：同样按「每组代表规则」展示，但不同
   公式命中同一只票会各留一行，所以「有效样本（票次）」可能大于「入选股票（只）」——
   这是真实的同票多规则语义（东财/同花顺的"多策略命中"同理），页面入口不经过这条路径。
